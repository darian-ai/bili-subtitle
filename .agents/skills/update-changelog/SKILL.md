# 更新 CHANGELOG

只更新当前 Git 仓库根目录的 `CHANGELOG.md`。不要提交、合并、切换分支、获取远程内容或修改其他文件。

## 检查仓库和输入

1. 用 `git rev-parse --show-toplevel` 确认当前目录属于 Git 仓库，并以返回目录作为项目根目录。
2. 读取当前分支、`git status --short` 和现有 `CHANGELOG.md`，不要覆盖未理解的人工内容。
3. 使用调用提示中明确指定的合并目标；未指定时使用 `main`。
4. 验证目标引用存在。目标不存在、仓库没有可用提交或无法计算 merge base 时，停止并说明需要用户提供什么；不要自行 fetch 或猜测其他目标分支。

## 收集变更

### 首次创建

当根目录没有 `CHANGELOG.md` 时：

1. 用 `git rev-parse --is-shallow-repository` 检查历史是否完整。若为 shallow repository，停止并说明无法可靠回填完整历史。
2. 检查 `HEAD` 可达的所有 non-merge commits；不要使用 `--all` 引入尚未合并的其他分支。
3. 读取每个 commit 的 author date、message 和实际 diff。不要只根据 commit message 猜测变更。
4. 同时检查 staged、unstaged 和 untracked 工作区变更。

### 更新现有文件

当根目录已有 `CHANGELOG.md` 时：

1. 用目标引用与 `HEAD` 的 merge base 作为本分支范围起点。
2. 检查该起点之后的所有 non-merge commits，包括 author date、message 和实际 diff。
3. 同时检查 staged、unstaged 和 untracked 工作区变更。
4. 将候选变更与现有日志做语义比较，只补充尚未记录的内容。

## 选择和归纳条目

- 记录所有实质变更，包括功能、修复、文档、构建、依赖、测试和开发体验改进。
- 忽略 merge commits、仅修改 `CHANGELOG.md` 的维护提交、纯格式化噪声和没有独立意义的生成文件变化。
- 当 lockfile 与依赖配置一起变化时，只概括实际依赖变更，不单独记录 lockfile。
- 在同一天内合并属于同一成果的 commits，并用结果或影响描述一次；不要机械翻译或逐条复制 commit message。
- 不跨日期合并条目。已提交变更使用 Git author date；未提交变更使用运行时的本地日期。
- 使用简体中文，保留文件名、命令、API、类、函数、依赖名、错误码和必要技术术语的英文形式；适合时用反引号标记这些标识。
- 使用具体、可验证的表述，避免“更新代码”“进行优化”等空泛描述。

## 写入格式

使用以下结构：

```markdown
# CHANGELOG

## 2026-08-20

- 建立项目愿景、路线图和技术栈规范。
- 搭建阶段一 Python 项目骨架，加入 CLI、测试与 CI 质量检查。
```

遵守以下规则：

- 日期标题固定为 `## YYYY-MM-DD`，按日期从新到旧排列。
- 每个日期只出现一次，日期标题与条目列表之间保留一个空行。
- 每条使用 `- ` 开头，以中文句号结束；不要添加“新增”“修复”等分类子标题。
- 若当天已有段落，将新内容合并到该段落；不要创建重复日期。
- 保留不冲突的人工说明和既有条目，只做完成任务所需的最小修改。
- 同一成果即使由多个 commits、工作区差异或多次调用重复发现，也只能出现一次。
- 没有未记录的实质变更时不要重写文件；文件不存在且没有可记录内容时不要创建空文件。

## 完成检查

重新读取 `CHANGELOG.md`，确认日期顺序、简体中文、必要英文标识和语义去重均正确。最后报告修改的日期段和新增或合并的条目数量；若没有修改，明确说明日志已经是最新状态。
