## 背景与目标

阶段二已经能够把用户输入解析为确定的普通 UGC 投稿和有序分集，但请求仍不携带账号登录状态。阶段三需要建立不要求用户手工复制 Cookie 的安全认证闭环：从 Windows Credential Manager 读取并验证已有会话；无有效会话时在终端显示二维码并以有界状态机等待扫码；成功后保存凭据，并使原主命令从认证检查之后自动继续一次。

完成后，用户可以显式执行 `auth login|status|clear` 管理单一默认账号，也可以在主命令需要认证时完成扫码并继续阶段二的元数据流程。阶段三不发现或下载字幕，不创建字幕输出。

## 范围

- 使用 `keyring` 访问 Windows Credential Manager，服务名称固定为 `bili-subtitle`，使用单一默认账号槽位。
- 定义会话凭据的最小序列化格式、严格解析、读取、保存和删除行为。
- 在 Bilibili 基础设施适配层实现登录状态检查、二维码申请、二维码轮询和登录成功凭据提取。
- 使用 `qrcode` 在终端渲染二维码，不写图片文件，不要求浏览器或 GUI。
- 实现有明确轮询间隔、总超时和取消处理的登录状态机。
- 接通 `bili-subtitle auth login`、`auth status` 和 `auth clear`。
- 为主命令增加认证编排：复用有效凭据，失效时登录，成功后继续原元数据任务一次。
- 使用测试替身覆盖 Credential Manager、HTTP、时间和终端交互；默认测试不得联网或读取真实凭据。

## 凭据模型与存储契约

- 凭据只保存恢复 Bilibili Web 会话所需的 Cookie 名值，不保存请求头、二维码密钥、二维码 URL、重定向历史或账号资料。
- 序列化对象必须有显式版本，Cookie 名和值均为字符串；空对象、未知版本、非法 JSON、字段类型错误或重复/不允许的结构均视为无效凭据。
- Cookie 集合采用确定性序列化，便于稳定测试；序列化文本本身属于秘密，不得进入日志、异常、对象表示或快照。
- 凭据端口只向应用层暴露读取、保存和清除操作；`keyring`、服务名和账号槽位只存在于基础设施层。
- 未找到凭据返回“未登录”语义；后端不可用、读取失败、保存失败和删除失败返回可区分的凭据存储错误，不伪装成未登录或成功。
- 无法解析的已存凭据不得发送到网络；应用应把它视为失效状态，并在自动流程中进入重新登录，在显式状态命令中报告凭据无效。
- `auth clear` 在凭据不存在时保持幂等并成功；其他删除失败必须明确报告。

## Bilibili 认证适配器

- 认证请求复用项目的同步 HTTPX Client 策略，使用统一请求头以及明确的连接、读取和总流程超时。
- 登录状态检查只返回稳定的认证结果与必要的非秘密展示信息，不向领域或 CLI 暴露原始响应、Cookie 或请求对象。
- 二维码申请结果分离可渲染内容与轮询密钥；二者只在单次登录生命周期内存活，不落盘、不进入长期领域模型。
- 轮询响应必须映射为未扫码、待确认、成功、过期、取消和失败六类稳定状态；未知结果码或结构变化属于平台响应错误。
- 登录成功时从受信任响应 Cookie 容器提取会话凭据；缺少完成会话所需 Cookie 时不得报告成功或保存半有效凭据。
- HTTP 状态异常、网络失败、权限或风控拒绝和响应结构异常必须分类处理，不透传远端响应正文，也不尝试 WBI、APP 私有接口或访问控制绕过。
- 轮询请求不得无限重试；只允许对明确瞬时网络失败做有限重试，且仍受总超时约束。

## 登录状态机

1. 显式登录或自动登录开始时申请一次二维码，并立即在终端显示安全提示和二维码。
2. 状态机按配置的固定间隔轮询；测试通过注入时钟或等待函数推进，不真实等待。
3. 未扫码时继续轮询；待确认时输出一次状态变化提示并继续轮询，避免每次轮询刷屏。
4. 成功时先校验并保存凭据；只有保存成功才向调用方返回已登录。
5. 二维码过期时明确终止当前尝试，不在同一命令中无限生成新二维码。
6. 用户通过 `Ctrl+C` 取消时返回取消结果，不打印堆栈，不保存或覆盖凭据。
7. 平台失败、未知状态、网络错误、凭据保存失败或到达总超时均明确终止。
8. 所有终止路径都不得输出二维码密钥、二维码 URL、Cookie 或底层响应正文。

## 认证命令契约

### `auth login`

- 先读取并在线验证已存凭据；有效时报告已经登录，不重新申请二维码。
- 没有凭据、凭据格式无效或在线检查判定失效时启动一次二维码登录。
- 登录成功且凭据保存成功返回 `0`；过期、取消、超时、平台或网络失败、存储失败返回 `2`。
- 失效旧凭据不得在新登录成功前被新值覆盖；如果新登录失败，命令不得留下半写入凭据。

### `auth status`

- 没有凭据时报告未登录；凭据格式无效时报告凭据无效；两者均不得发起二维码登录。
- 存在可解析凭据时执行在线状态检查，区分有效和已失效。
- 有效登录返回 `0`；未登录、无效或已失效凭据返回 `1`；网络、平台结构或存储错误返回 `2`。
- 输出只包含稳定状态和经过控制的非秘密账号展示信息；不得输出完整账号响应或 Cookie。

### `auth clear`

- 删除默认账号槽位中的凭据，不调用 Bilibili 注销接口，不访问网络。
- 凭据存在或原本不存在都返回 `0`，并给出明确结果。
- Credential Manager 删除失败返回 `2`，且不得声称已经清除。

## 主命令认证编排

- 主命令在完成输入解析、并即将执行需要账号状态的应用请求前读取并验证凭据；CLI 不直接访问 keyring 或认证接口。
- 有效凭据被注入同一次 HTTP 会话并继续阶段二元数据流程，不显示二维码。
- 凭据缺失、格式无效或在线判定失效时启动一次二维码登录；成功保存后继续原任务一次，用户无需重新执行命令。
- 恢复流程必须保留原输入和分集选择参数，不重新解释或扩展任务，也不得重复执行已经产生副作用的步骤。
- 登录后若原请求仍返回认证失效，只返回明确整体失败，不在同一命令中再次启动登录循环。
- 阶段三主命令成功仍只输出阶段二元数据摘要并返回 `0`；认证或元数据整体失败返回 `2`，不创建 `subtitles/`。

## 已确定决策

1. 阶段三使用 `keyring` 作为唯一凭据持久化入口，不提供环境变量、命令行 Cookie、明文文件或自定义路径降级方案。
2. V1 只管理单一默认账号槽位，不增加账号选择、账号列表或多账号切换。
3. 登录状态的权威证据是在线状态检查，不以“Credential Manager 中存在字符串”推断有效登录。
4. 二维码只在终端渲染；二维码内容本身视为秘密，不打印其原始文本，也不保存图片。
5. 二维码过期、取消或超时结束当前尝试；需要重试时由用户重新执行命令，以保证流程有界。
6. `auth status` 用退出码 `1` 表示可预期的未登录状态，用 `2` 表示无法得出可靠状态的操作错误。
7. 主命令的自动恢复只允许一次，防止认证检查与重新登录形成无限循环。
8. 认证领域结果使用标准库类型表达，不把 keyring、HTTPX、Typer、Rich 或平台响应对象带入领域层。

## 不在范围内

- 字幕轨道发现、正文下载以及 JSON、SRT、manifest 写入。
- 多账号、账号切换、Cookie 导入导出、浏览器 Cookie 读取或跨设备同步。
- 密码、短信、浏览器自动化、第三方登录或 Bilibili 注销接口。
- 二维码图片文件、GUI、Web 回调服务或自动打开浏览器。
- 长期保存二维码密钥、二维码 URL、请求头、账号资料或完整登录响应。
- 付费、地区、会员、风控或其他访问控制绕过。
- 并发轮询、后台刷新服务、定时任务或无限自动重试。

## 安全与兼容约束

- Cookie、序列化凭据、二维码密钥和二维码原始内容不得出现在标准输出、标准错误、日志、异常文本、对象表示、测试快照或普通配置文件中。
- 自动化测试只使用明显的伪秘密，并必须断言所有捕获输出与异常不包含这些值。
- 默认测试不得读取或修改真实 Windows Credential Manager；keyring 后端和认证网络必须完全替换。
- 凭据保存失败时不得报告登录成功；所有远端和本地输入都必须在进入应用结果前严格校验。
- 新增直接运行时依赖只允许 `keyring` 和 `qrcode` 及其必要传递依赖，不得引入浏览器自动化、媒体下载、ASR、OCR 或绕过工具。
- Windows 是真实 Credential Manager 验收平台；除凭据适配器外，状态机和认证编排保持可移植、可离线测试。
